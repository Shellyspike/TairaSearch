# Универсальная настройка исследования через Codex

[English version](research-onboarding.md)

TairaSearch 0.3.1 использует локальный исследовательский профиль поверх
существующего FTS5-индекса. Схема SQLite, `chunk_id`, `daily-five` и
`used_finds.csv` не меняются.

## Быстрый запуск без ручной настройки

1. Скачайте проект и подготовьте `.venv` по [README.ru.md](../README.ru.md).
2. Откройте папку в приложении Codex.
3. Вставьте целиком
   [`examples/codex/research-onboarding.ru.md`](../examples/codex/research-onboarding.ru.md).
4. Укажите существующий индекс или папку корпуса и ответьте на несколько
   обычных вопросов об интересах.
5. Проверьте пробные находки и при необходимости скажите, что изменить.

Пользователь не редактирует конфигурацию. Codex после подтверждения сохраняет
её в игнорируемый Git файл `research_profile.json`.
Точная схема показана в двух тестовых примерах из
[`examples/profiles/`](../examples/profiles/); пользователю не нужно их
редактировать.

## Что хранится в профиле

Профиль — небольшой проверяемый JSON со следующими полями:

- `research_area` и язык результата;
- `interests`: понятные названия интересов и подтверждённые поисковые термины;
- необязательные `focus_people` и варианты имён;
- типы материалов;
- желаемый характер находок и настройка разнообразия;
- количество результатов, по умолчанию пять, но допустимо от одного до двадцати.

На результат влияют только поля, которые действительно использует поиск.
Codex должен переводить свободное пожелание пользователя в подтверждённые
`interests[].terms`, вес интереса `weight`, типы материалов или фильтры
источников. `finding_preferences.notes` — лишь пояснение: оно не влияет на
ранжирование и фильтрацию, поэтому сохранить пожелание только в `notes`
недостаточно.

Файл не меняет аннотации индекса. Новые имена и темы используются как FTS-запросы
к уже сохранённому тексту, поэтому пробный поиск не требует переиндексации.
Если нужны новые индексные аннотации для других CLI-команд, это отдельное
изменение и его нельзя применять к production без проверки на копии.

## Безопасная первичная индексация

Если индекс уже существует, onboarding использует его только для чтения. Если
есть лишь папка корпуса, сначала выполняется безопасное сканирование:

```powershell
.venv\Scripts\python build_index.py "ПУТЬ_К_КОРПУСУ" --scan-only
```

Только после согласия пользователя создаётся новый индекс в `work/`, без
`--rebuild` для существующей базы. Недоступные или исчезнувшие документы не
удаляются автоматически.

## Пробная подборка

Пример команды, которую запускает Codex:

```powershell
.venv\Scripts\python taira_search.py research-findings --db work/research/index.sqlite3 --profile research_profile.json --used-finds used_finds.csv --output work/research/candidates.json --preview
```

`--preview` не добавляет записи в журнал. На самом деле сама команда
`research-findings` только читает `used_finds.csv`; публикация остаётся
отдельной явной операцией. JSON содержит полный соседний контекст и отчёт о
предпочтениях, для которых индекс не дал совпадений. Поле `final` —
Python-шортлист, а не окончательное редакционное решение; Codex также проверяет
`alternates` и свидетельства в `semantic_review`.

После обратной связи Codex меняет профиль и повторяет preview. Например,
«меньше военных событий» меняет интересы/веса, а не Python-код или только
пояснительное поле `notes`.

## Продолжение после редакционного отказа

Если Codex после проверки источников или смысловой новизны отклонил первую
партию, он не останавливается, а запрашивает следующую непересекающуюся:

```powershell
.venv\Scripts\python taira_search.py research-findings --db work/research/index.sqlite3 --profile research_profile.json --used-finds used_finds.csv --output work/research/candidates-2.json --preview --continue-from work/research/candidates.json
```

Предыдущий JSON хранит показанные и технически отклонённые `chunk_id`.
`--continue-from` исключает их, но оставляет доступными проверенные кандидаты,
которые ещё не были показаны. Флаг можно повторять для следующих партий. Если
текущая глубина выдачи исчерпана, Codex может один раз ограниченно увеличить
`--top-per-interest` или `--pool-size`, не меняя профиль. Пустая партия не
является ошибкой индекса, а ошибку чтения индекса или данных нельзя выдавать за
пустой результат.

## Последующие ручные запуски

Сохранённый профиль повторно используется той же командой
`research-findings`. Флаг `--preview` опускается только для подборки,
предназначенной для обычного редакционного процесса. Сам поиск всё равно лишь
читает `used_finds.csv`: он не публикует карточки и не дописывает журнал.
Codex следует готовому
[`examples/codex/research-workflow.ru.md`](../examples/codex/research-workflow.ru.md):
сам управляет последовательными вызовами `research-findings`, проверяет
источники и четыре класса смысловой новизны 0.3 и окончательно выбирает
находки. Только явный запрос на публикацию ведёт к сохранению манифеста под
`work/` и существующей команде `record-publication`, как описано в
[ai-workflow.md](ai-workflow.md). Нормальны от одной до заданного максимума
сильных находок и пустая подборка.

Это ручной сценарий. Версия 0.3.1 не создаёт расписание и не меняет существующие
автоматизации Codex.

## Два воспроизводимых сценария

```powershell
.venv\Scripts\python run_research_demo.py
```

Сценарий `japan` использует существующий синтетический корпус, отмечает Тайра,
Ёсицунэ и Дзэами как интерес, но допускает других персонажей. Отчёт честно
показывает, если некоторые имена не встретились. Сценарий `rome` использует
отдельный синтетический римский корпус и профиль без единого заранее заданного
персонажа. Результаты сохраняются только в `work/research-demo/`.
